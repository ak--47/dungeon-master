# 1.9.0 upgrade guide

1.9.0 collects the engine fixes found while rebuilding the 22 vertical dungeons.
The public exports, function signatures, and config keys are unchanged. Most
fixes change generated output for a fixed seed, so every story band measured on
1.8.5 needs a fresh measurement.

This version is unreleased. It is prepared on the release branch. After npm
publication:

```sh
npm install @ak--47/dungeon-master@1.9.0
```

Update the consumer's lockfile and record the resolved version in run metadata.
An existing lockfile resolving 1.8.5 does not change just because its dependency
range permits 1.9.0.

## output changes for a fixed seed

Do not compare 1.8.5 and 1.9.0 output byte for byte. Two kinds of change apply:

1. **Value changes.** A field takes a different value by design (born `created`
   time, device fields, browser, experiment exposure count).
2. **RNG stream shifts.** A fix takes fewer or more seeded draws (sticky device
   fields, repeated funnel steps, world-event clone times). Every seeded value
   after that point changes, even in fields the fix does not touch.

Within 1.9.0 the old contract holds: same seed, same config, pinned dates, and
`concurrency: 1` give identical output, including `insert_id`.

| config | affected by |
| --- | --- |
| any config | UTC time model, born `created` time, uniform births, day-0 lead-in, `hashFloat` |
| born users, legacy mode | first funnel pinned to `created` |
| `avgActiveDaysPerUser` or `retentionCurve` | flat pre-existing activity, born per-day intensity, catch-all plan days, weekday weights applied once |
| no `isAuthEvent` declared | born profiles kept, events carry `user_id` (21 technical fixtures, no vertical) |
| first funnel with steps after the `isAuthEvent` | drop-offs after the stitch run usage funnels |
| a device switch (`hasIOSDevices`, `hasAndroidDevices`, `hasDesktopDevices`) | sticky device fields, platform family, RNG shift |
| `hasBrowser` with a device switch | browser per OS |
| `avgDevicePerUser` fractional above 1 | pool mean honored |
| `experiment` on a funnel | one exposure per user, 1s lead, budget-neutral variants |
| an event `weight` above 10 | event mix changes |
| repeated funnel steps, including the catch-all funnel | conversion and step counts change |
| `bindPropsIndex` | binding counts real steps |
| `worldEvents[].volumeMultiplier > 1` | clone bounds, properties, and times |
| `engagementDecay` | keeps the signup and stitch |
| `personas` | profiles lose `_persona` |
| `warehouseMetrics` with `users` or `dau` | anonymous identities resolve |

On `dungeons/technical/simplest.js` (2,000 users) events rose 1.8% (187,270 to
190,565) from the repeated-step fix alone. The event mix moved by at most 0.2
points.

## time model

### time-zone independence

Born users' `created`, SCD rows, ad-spend dates, mirror cutoffs, and the
`day()`, `datesBetween()`, and `dateRange()` helpers now use UTC. The same seed
and config give byte-identical output under any `TZ`. A 1.8.5 run on a non-UTC
host can differ from a 1.8.5 run on a UTC host; 1.9.0 removes that difference.

### born `created` time of day and day of week

| | 1.8.5 | 1.9.0 |
| --- | --- | --- |
| `created` time of day | calendar-day boundary | seeded, weighted by the soup hour-of-day curve |
| birth day | uniform day pick | weighted by the soup day-of-week curve |
| `bornRecentBias` | separate adjustment | a density in the same draw |
| first and last window day | half weight (rounding error) | full weight |

Births are now uniform across the window, edge days included.

### first funnel pinned to birth

A born user's first funnel starts at `created` in every mode. Legacy mode (no
`retentionCurve`, no `avgActiveDaysPerUser`) placed the signup a median of ~24
days after birth, which piled volume at the right edge. In
`avgActiveDaysPerUser` mode the birth day now opens the active-day plan.

### day-0 lead-in

The first window day ran light (about 0.77-0.86 of the interior mean).
Pre-existing users now generate a short lead-in before the window, as long as
the longest usage funnel's `timeToConvert`. Funnel steps spill into day 0 as
they do into every other day. The engine drops lead-in events before hooks run,
so hooks never see them.

### SCD history

Pre-existing users' SCD history starts before the window. No SCD row starts
after the window end. A born user's first SCD row is at or after `created`.

## identity

### experiment exposure

| | 1.8.5 | 1.9.0 |
| --- | --- | --- |
| `$experiment_started` count (sticky) | one per qualifying funnel run | one per user per experiment |
| position | took the step-0 slot | 1 second before the first real step |
| start-date gate (legacy mode) | user's first event time | the run's real first-step time |
| counts against event budget | yes | no |

The step-0 slot pushed the real first step one variant-scaled step later. A
funnel measured from exposure showed a false variant effect. Later runs keep the
variant and its multipliers but send no exposure. `worldEvents` clones skip the
exposure, and `engagementDecay` never drops it. `sticky: false` experiments keep
one exposure per run, because each run re-rolls the variant.

Devtools vertical before the fix: 88,965 exposures for 7,425 users.

### pre-auth steps on the stitch device

With several devices, a born user's pre-auth first-funnel steps (every attempt)
carry the stitch event's `device_id`. Before, a first visit that crossed UTC
midnight split into two sessions and the pre-midnight steps got another device.
Without `hasSessionIds` every pre-auth step drew a random device. Those
anonymous rows never stitched. Repro with 1,600 born users and 3 devices: 1,625
pre-auth events off the stitch device without session ids; now 0.

### configs without `isAuthEvent`

With no stitch step, 1.8.5 marked every born profile `_drop` (never sent to
/engage). With a device pool it also stripped first-funnel, standalone, and
usage events to `device_id` only. 1.9.0 identifies born users from their first
event. Every event carries `user_id` and the profile is kept. Hook
`meta.authTime` is the first event's time. Configs with an `isAuthEvent` are
byte-identical for this fix.

### drop-off after the stitch

A born user who reached the `isAuthEvent` stitch and dropped at a later
first-funnel step now runs usage funnels like any identified user. Before, any
first-funnel drop-off left the user with one-at-a-time standalone events for
life. With the auth step first (social, support-desk), born members fired ~4x
the standalone events of established members (199 vs 51 per 1k views); now 50
vs 49. A born user who dropped before the stitch is unchanged: anonymous,
device-only standalone events, profile `_drop`.

## activity shape

| change | modes | effect |
| --- | --- | --- |
| pre-existing activity stays flat | `avgActiveDaysPerUser`, `retentionCurve` | rounding leftovers no longer pile onto the earliest days |
| `retentionCurve` shapes born users only | `retentionCurve` | pre-existing users take their day count from the curve, but their days follow day-of-week weight |
| born per-day intensity matches established users | `avgActiveDaysPerUser`, `retentionCurve` | born/established events per active day 0.71-0.78 before, 0.97-1.06 now |
| catch-all steps take their own plan day | `avgActiveDaysPerUser`, `retentionCurve` | median active days 10 before, 30 now, against a plan of 31 |
| soup hour shape on catch-all steps | legacy | hour correlation -0.09 before, 0.999 now |
| weekday weights applied once | `avgActiveDaysPerUser`, `retentionCurve` | 2.5x configured gave 4.7-5.4x before, 2.2-2.5x now |
| `engagementDecay` keeps the signup | any | never drops `isFirstEvent` events or the stitch; born decay anchors on the first emitted event |

Consequences for stories:

- Build retention stories on born users. Pre-existing users no longer age from
  the window start.
- `retentionCurve` sets how many days a born user is active, not how busy each
  day is. Run totals rise with a steeply decaying curve and barely move with a
  flat one.
- In `avgActiveDaysPerUser` mode born users have fewer active days, because the
  mean scales with the share of the window they are alive for.
- Born-user day-1 retention now tracks the curve (0.45 against a configured
  0.5, was 0.81).

## devices

| | 1.8.5 | 1.9.0 |
| --- | --- | --- |
| `model`, `os`, `screen_height`, `screen_width`, `carrier`, `browser` | re-drawn per event (~16 models per `device_id`) | seeded hash of the `device_id`, sticky |
| events without a `device_id` | random device | the user's primary device |
| no device pool | random per event | sticky per user |
| `radio` | per event | per event (unchanged) |
| `browser` | one mixed list | pool valid for the device `os` |
| extra devices (`avgDevicePerUser > 1`) | independent OS per device | same platform family as the primary (~6% still draw from the whole pool) |
| `avgDevicePerUser: 1.3` | rounded to 1 silently | mean pool size 1.3 (300 users: 1.45 devices) |
| `avgDevicePerUser` between 0 and 1 | rounded silently | rounded, plus a `result.warnings` entry |

Default shares are fixed by record weights (before, random `weighArray`
copies set them per seed):

| | 1.8.5 (fitness, media, ecommerce; 2,000 users) | 1.9.0 |
| --- | --- | --- |
| mobile users iOS / Android | 39-50% / 50-61% | ~55% / ~45% |
| iPad-only share of Apple users | 11-36% | ~5% (iPads are mostly an extra device) |
| desktop events Windows / macOS / Linux | 60-65% / 25-29% / 7-11% (incl. PureOS, Pop!_OS) | ~70% / ~26% / ~4% (`os: 'Linux'`) |
| Windows browsers | Chrome 45%, Opera GX 6% | Chrome 65%, Edge 20%, Firefox 8%, no Opera GX |
| macOS browsers | Safari 32%, Chrome 32% | Safari 50%, Chrome 40% |

Configs with no device switch or desktops only keep their RNG stream. Configs
with iOS or Android devices shift it (per-event `radio` draws follow the mobile
mix). Hooks that branch on `os === 'PureOS'` or `'Pop!_OS'` now see `'Linux'`.

Device fields follow the `device_id` through the per-session device pass. Event
props, super props, and `event`/`everything` hook edits of the same name still
win. A hook that changes an event's `device_id` owns the device fields on that
event. Without a device switch, `browser` still comes from the mixed list.

## `worldEvents` clones

For `volumeMultiplier > 1` (and `aftermath.volumeMultiplier`):

- Clones stay inside the user's lifetime: not before the first event or the
  stitch, not after churn or `FIXED_NOW`.
- Clones re-draw the event's declared `properties` from config, in declaration
  order. `(ctx) => value` functions see the clone and its time. Identity, super
  props, `stickyEventProps`, group keys, funnel `props`, and UTM fields are kept.
  `injectProps` active at the clone's time are re-applied.
- Clone times follow the soup hour and weekday weights. A 4x world event gave
  hour peak/trough 1.37x against 3.57x configured; now 3.68x.
- The `event` hook does not run on clones. Shape them in `everything`.
- Identity follows the clone's own time. A clone of a born user's pre-auth
  (device-only) step that lands after the stitch carries `user_id` and keeps the
  stitch `device_id`. A hook that stamps `user_id` on post-signup device-only
  clones (ecommerce) can drop that line.

## experiments

- **Budget-neutral variants.** The user loop runs funnels until the event budget
  is spent, so a better-converting variant ran fewer funnels. An experiment run
  is now charged at its expected step count under the pre-experiment rate. Both
  arms run the same number of funnels (2.5x variant: deposits per user 16.6 vs
  21.3 before, 20.3 vs 20.4 now). Variant users who convert more now emit more
  events, so `numEvents` overshoots a little when a variant lifts conversion.
- **No 0.1-hour TTC floor.** `timeToConvert` after a variant `ttcMultiplier` or
  a persona `ttcModifier` is no longer floored at 0.1h. 0.15h x 0.6 is now 0.09h.

## funnels and weights

- **Repeated steps keep the configured conversion.** With `requireRepeats:
  false`, each skipped repeat multiplied the rate by 0.70 (and each kept one by
  1.35). The drop-off point was drawn on the full length but applied to the
  shortened list. Repeats are still skipped on a 50% draw, but conversion and
  drop-off use the full sequence, and the last step is never skipped. A
  `conversionRate: 100` first funnel with a repeat before its `isAuthEvent` now
  stitches every born user (marketplace: 128 of 3,000 profiles were dropped).
- **`bindPropsIndex` counts real steps.** The prepended `$experiment_started`
  shifted the index by one. Steps before the index now keep their own declared
  value of a funnel prop key; before, the key was removed. `$experiment_started`
  never carries funnel `props`.
- **Event weights are uncapped.** Weights were clamped to [1, 10] without a
  warning, so weight 26 equaled weight 10. Weights are now whole numbers >= 1
  with no upper cap. A floored fraction or a value below 1 lands in
  `result.warnings` as `events[<name>].weight`. Dungeons with a weight above 10
  change their event mix.

## `hashFloat` finalizer

`hashFloat` (and so `hashCohort` and `applyPathBias`) adds a murmur3 fmix32
finalizer after FNV-1a. Salted keys such as `${uid}|a` and `${uid}|b`
correlated at |r| 0.05-0.10, so one hidden cohort leaked into another. Salted
splits are now independent.

Every hash value changes. A user in a `hashCohort(uid, 20)` cohort on 1.8.5 may
be outside it on 1.9.0. Membership still nests (`pct=5` is a subset of
`pct=20`), and the share is still ~`pct`%.

## profiles: no `_persona`

The engine no longer writes an internal `_persona` field on profiles. A persona
with no `properties` got `properties: {}` from the validator, so the field
always exported and imported as a visible profile property.

Read the persona in hooks from `meta.persona` on `user`, `funnel-pre`,
`funnel-post`, and `everything`. To segment by persona in reports, declare a
persona `properties` key:

```js
// before: hook reads an internal field
if (profile._persona === 'hardcore') { ... }

// after
if (meta.persona?.name === 'hardcore') { ... }

// and, for reports
personas: [{ name: 'hardcore', weight: 30, properties: { player_type: 'hardcore' } }]
```

## warehouse metrics

- `users` and `dau` measures resolve identity the way Mixpanel ID merge counts
  users: `user_id`, else the user whose stitch event carried the `device_id`,
  else the `device_id`. Before, every device-only event fell into one `''`
  identity (1,000 anonymous visitors read as 1 user). The offline verifier
  (`computeWarehouseSourceRows`) uses the same rule. Events are unchanged.
- `source.groupBy` and `source.property` accept a `stickyEventProps` key or a
  group key stamped on every source event. Configs that threw now run.
- `scripts/verify-stories.mjs` reads gzipped shards (`.json.gz`, `.csv.gz`) for
  events, profiles, and warehouse tables from any directory prefix.
- Manifest `bqType` is `INT64` for a numeric column whose values are all whole
  numbers, else `FLOAT64`. `avg` and `dau` value columns, and value columns of
  empty tables, stay `FLOAT64`. Rows are unchanged. A whole-valued price column
  also lands as `INT64`; BigQuery `/` still returns `FLOAT64`.

## sessions

The engine re-stamps `session_id` after `everything`. An event that the
`everything` hook stripped of `session_id` (a server-side event) now stays
stripped. It still shapes the other events' sessions. Only dungeons whose
`everything` hook deletes `session_id` change.

## verifier

- **Wrong-shaped funnel step filters throw.** A step filter must be
  `{ prop, op, value }`. A map-shaped `where` used to match every event
  silently.
- **`between` bands grade STRONG past the far edge.** A value that passes the
  floor grades STRONG. The floor is `floor`, else the band edge on the weak
  side. A stronger effect than designed used to grade WEAK (ratio or difference)
  or NONE (single ref). On a single-ref metric `floor` gives the effect
  direction; without it, outside the band stays NONE.

  ```js
  // designed drop to 0.30, observed 0.267
  expect: { op: 'between', target: [0.27, 0.33], floor: 0.4 }
  // 1.8.5: WEAK (ratio) or NONE (single ref). 1.9.0: STRONG.
  ```

- **New archetype `external-join`.** Use it for a story whose evidence joins
  events with a `warehouseMetrics` table. Assert with `warehouse` or
  `warehouse-stats` breakdowns, or `duckdb` SQL over both. The archetype enum
  now has 15 values.

## engine-shape bars

Strict-bar condition 2 (the last-day check) in `tests/engine/sweep-engine.mjs`
and the canary changed:

| | 1.8.5 | 1.9.0 |
| --- | --- | --- |
| compare last day with | the same weekday one week earlier | the same weekday averaged over up to 4 prior weeks |
| bar | 0.7 (0.6 in `avgActiveDaysPerUser` mode) | 0.5 (0.45 in `avgActiveDaysPerUser` mode) |

The one-week comparison had day-to-day noise of sd ~0.24 and failed decline
runs by chance. The other five conditions are unchanged.

## remove these workarounds

Delete hook code that patched these 1.8.5 behaviors. Leaving it in place now
double-corrects.

- [ ] Hooks that re-time born users' signup or first funnel to `created`, or
      move `created` off midnight.
- [ ] Hooks that re-time SCD rows to start before the window or at `created`.
- [ ] `everything` filters that drop `worldEvents` clones before the first
      event, before the stitch, or after churn.
- [ ] Hooks that re-draw property values on `volumeMultiplier` clones.
- [ ] Hooks that stamp `user_id` on device-only `volumeMultiplier` clones
      that land after the stitch (ecommerce).
- [ ] Hooks that dedupe `$experiment_started` to one per user, or move it ahead
      of step 0.
- [ ] Hooks that pin `model`, `os`, `browser`, or screen fields per `device_id`,
      or fix impossible browser/OS pairs.
- [ ] Hooks that move pre-auth first-funnel rows onto the stitch `device_id`.
- [ ] Hooks that re-add events to day 0 or thin the right edge to undo the
      legacy-mode signup pile.
- [ ] Hooks that restore the signup or stitch after `engagementDecay`.
- [ ] Local hash mixers wrapped around `hashFloat` to decorrelate salted keys.
      Pass salted keys to `hashFloat` directly.
- [ ] Code that strips `_persona` from profiles before export, or reads
      `profile._persona`. Use `meta.persona`.
- [ ] Event weights held at 10 because of the old cap. Set the weight you want.
- [ ] Integer-rounded `avgDevicePerUser` values chosen because fractions were
      ignored.
- [ ] Hooks that delete `session_id` a second time after the engine re-stamp.

## re-verify

1. Regenerate each dungeon at full scale with pinned dates and the same seed:
   `node scripts/verify-runner.mjs <path> [prefix]`.
2. Run `node scripts/verify-stories.mjs <path> --data-prefix <prefix>`. Expect
   bands measured on 1.8.5 to move.
3. Re-derive each story's `target` and `floor` from the exported knob constants
   the hook uses, not from 1.8.5 observations. Set `between` floors on the weak
   side of the band.
4. Re-run `/verify-dungeon` for schema integrity. Check the identity invariants:
   stitch count, born profile count (no-`isAuthEvent` configs now keep born
   profiles), and one `$experiment_started` per user per sticky experiment.
5. For warehouse dungeons, re-emit the tables and re-check `users` and `dau`
   metrics before a `/warehouse-metrics` deploy.
6. Re-import to Mixpanel only after the offline stories pass. A re-import into a
   project loaded with 1.8.5 data does not dedupe, because `insert_id` values
   change with the RNG stream.

## known issues

- With no `soup` config, active-day modes (`avgActiveDaysPerUser`,
  `retentionCurve`) show almost no weekly rhythm (1.11x weekday ratio against
  the default 1.89x). A fix exists but makes three steady combos miss the l7c
  bar (0.496 against 0.5); it awaits owner approval to relax that bar.
