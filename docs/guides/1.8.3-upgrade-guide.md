# 1.8.3 upgrade guide

1.8.3 fixes generation-time windows and timestamp piles at dataset boundaries.
Relative dungeons now end at the instant captured when generation starts.
Absolute dates retain their UTC calendar-day meaning. The public exports,
function signatures, dependencies, and verifier counting defaults are unchanged.

This version is prepared for release. After npm publication:

```sh
npm install @ak--47/dungeon-master@1.8.3
```

Update the consumer's lockfile and record the resolved version in run metadata.
An existing lockfile resolving 1.8.2 does not change just because its dependency
range permits 1.8.3.

## rolling windows end at generation start

With `numDays` and no explicit dates, the engine captures the current instant
once in epoch seconds:

```text
datasetEnd = runStart
datasetStart = runStart - numDays * 86400
```

Previously, the fallback used the host's local midnight. A run later that day
could omit many hours. UTC and non-UTC hosts could also choose different windows.

Use `result.validatedConfig.datasetStart` and `datasetEnd` as the authoritative
resolved bounds. The end does not advance during generation or import. Events
can occur throughout the final partial day; a sparse dataset need not contain
an event at the exact endpoint.

The relative start can be mid-day too. This is a rolling duration, not N complete
calendar days. A partial day's low count is expected; compare equal observed
durations or complete bins when measuring daily trends.

## exact dates still mean complete UTC days

| input | interpretation |
| --- | --- |
| `datasetStart: '2026-09-01'` | September 1 at 00:00:00 UTC |
| `datasetEnd: '2026-09-13'` | September 13 at 23:59:59 UTC |
| ISO string with a time and offset | the specified instant, normalized to epoch seconds |
| numeric seconds or milliseconds | the specified instant, normalized to epoch seconds |

Both explicit bounds must be provided together. The engine derives `numDays`
from their span and ignores a conflicting supplied day count.

A bare end date of today includes future time until UTC midnight. File generation
can preserve that requested window. Before live import, reject a future window or
ask the operator to change the effective bounds. Do not collapse future rows to
now or claim that a filtered import is identical to a full future-dated preview.

## sampling no longer pushes overflow onto the edge

Three mechanisms contributed to endpoint piles:

1. Active-day plans included a zero-duration UTC day when the end was midnight.
2. A partial day received a full day's event allocation.
3. TimeSoup clamped Gaussian overflow and unavailable hour-of-day samples to
   window boundaries.

1.8.3 excludes zero-duration day buckets. It thins partial-day slots once by
their available duration and reassigns unused slots to full days. This preserves
the planned budget when full-day capacity exists. A selected partial day may
receive no events; a replacement full day can increase the selected-day count.
When a user's entire lifetime has no full day, a finite event budget must fit
within that short interval. Uniform event density is not guaranteed there.

TimeSoup reflects Gaussian overflow within the selected chunk. Hour sampling
uses only the available interval, weighted by its duration and configured hour
weight. Fractional peak counts are normalized to whole chunks that fit the range.
If the selected partial day has no positive-weight hours, TimeSoup uses eligible
hours elsewhere in the requested interval. It throws `RangeError` if none exist
anywhere. A zero-duration request still returns its one possible instant.
Active-day scheduling excludes days with no permitted hours and skips slots
whose remaining hours are unavailable after onboarding.

The final future-event guard remains. Late funnel steps and hook clones beyond
the dataset end are dropped, not retimed onto it. Long funnels can therefore
have right-censored completions near the endpoint. Use mature entrants for
acceptance when the report needs a full conversion opportunity.

The early funnel guard now compares milliseconds too. Previously, rounding down
to seconds could let a step up to 999 milliseconds past the bound reach full-stream
hooks before final storage removed it. This caused a retained high-density timing-hook
proof to fail; the same cell passes with the precision repair. Per-event hooks
still run before the generator marks that step for removal.

## seed reproducibility requires a pinned window

Timestamp and RNG changes mean the same seed can produce different output from
1.8.2. Do not compare cross-version byte equality. Within 1.8.3, use the same
pristine config, pinned dates, seed, and `concurrency: 1`. Exclude only the fresh
`insert_id` values when comparing generated events.

For calibration, resolve a relative window once and pin it across candidates.
For a later production run, resolve a fresh window and verify that final artifact.
Do not let a UI's stale module cache or previously normalized config silently
reuse an older relative window.

## a configured multiplier is not a report result

Read the [counting contracts](../alignment/counting-contracts.md) and
[story recipes](../alignment/story-recipes.md) before calibrating a story.

- `conversionRate` controls an offered attempt. Repeated attempts can make
  unique-user conversion approach 100% in every segment or experiment arm.
- A profile device pool does not establish an identity link. If authentication
  is the final funnel step, profile-only segments can omit anonymous failures.
  Use a declared sticky entry-event property when that is the intended segment.
- `retentionCurve` contains active-day selection weights, not literal D1, D7,
  or D30 report percentages. Event budgets, calendar alignment, funnel spill,
  and mature cohort selection affect the observed rates.
- Shared event names can complete more than one funnel. Distinct funnel names
  or IDs do not isolate report histories.
- Incident measurement must use the resolved incident window. Inferring it from
  the last observed target event moves the window on sparse or partial data.

The README and hook reference now qualify older retention claims. There is no
universal 85% D1 floor or fixed correction factor. This release does not introduce
literal retention-probability calibration or change the verifier's defaults.

## consuming UIs need separate verification stages

1. Run previews in isolated jobs with current source/spec hashes. Re-importing
   the same file URL in a long-lived Node process can execute cached source.
2. Preserve per-user density, history duration, identity, and report settings
   when shrinking a preview. Count eligible entrants and mature users, not events.
3. Verify the final full-scale output after hooks, bounds, identity processing,
   and serialization. Import that same artifact.
4. Check import receipts and query readiness, then measure native Mixpanel reports
   with matching options. An import acknowledgement does not prove identity readiness.

The Mixpanel [import contract](https://docs.mixpanel.com/reference/import-events#properties)
says future timestamps can be overwritten with ingestion time. `strict: false`
does not guarantee preservation. The current sender additionally supplies an
import-time epoch cutoff to mixpanel-import, which filters later rows locally.
Keep generated, filtered, submitted, and query-visible counts separate.

## validation and evidence scope

Focused tests cover captured run start, host-timezone-independent relative
resolution, unchanged absolute-date parsing, full/partial UTC day allocation,
one-second and half-day endpoints, Gaussian boundaries, fractional peaks, and
hour-weight support. The existing 194-case engine shape matrix passed after
these repairs. It does not cover every dungeon or hook combination.

A retained 8,000-user DexCare run produced 1,351,831 events with no out-of-window
rows or exact endpoint pile. It also demonstrated why app changes remain needed:
entry-event segments showed 49.51% versus 20.81% care conversion, while profile
segments showed 100% versus 100%. Repeated intake attempts yielded only 1.0079x
unique-user experiment lift, and mature D7 retention measured 33.07% against an
18% scheduling anchor. Its correctly located campaign measured 3.2558x against 3.2x.

These are local measurements. The retained [live report](../alignment/live-report.md)
describes 1.8.2 counting evidence, not a fresh live comparison for 1.8.3. No npm
publication, live import, project modification, or DM4 deployment is implied.
